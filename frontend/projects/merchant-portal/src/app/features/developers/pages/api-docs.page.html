Advancing a sandbox order

A sandbox order stays in CREATED until you move it. Each call to POST /merchant-api/sandbox/orders/{trackingNo}/advance moves it one step along CREATED, ASSIGNED, PICKED_UP, IN_TRANSIT, OUT_FOR_DELIVERY, DELIVERED. Send the body { "outcome": "FAILED", "reason": "..." } to simulate a failed delivery. Advancing an order that is already finished returns 409 INVALID_STATE, and a live key gets 403 SANDBOX_ONLY.

Authentication

Use one of two methods. Both are tied to your merchant account and environment.

API key

Send the key in the X-API-Key header. Keys look like sd_live_ab12cd34_... and are shown once when created. Rotate a key to get a replacement; the old key keeps working for the grace period you choose (0 to 72 hours).

OAuth 2.0 client credentials

Exchange a client ID and secret for an access token that is valid for one hour. Send the credentials with HTTP Basic authentication or as the form fields client_id and client_secret. The optional scope must be a subset of the client's scopes (orders:write, orders:read).

Then send the token as a Bearer token. Request a new one shortly before it expires.

Token errors follow RFC 6749: 400 with invalid_request, invalid_grant, unsupported_grant_type or invalid_scope, and 401 invalid_client when the client ID or secret is wrong or the client or merchant is not allowed to use the API.

A new order returns 201 with the order, including its trackingNo, a public trackingUrl to share with the recipient and the fee.

Idempotency

Send an Idempotency-Key header (a UUID works well) with every order so a retry after a timeout never creates a second parcel. Keys are unique per merchant.

  • Same key and same payload: you get the original order back with 200 and the header Idempotent-Replayed: true.
  • Same key and a different payload: 422 IDEMPOTENCY_KEY_REUSED.
  • Same key while the first request is still running: 409 IDEMPOTENCY_KEY_IN_USE with Retry-After: 1.
  • A failed attempt (422 PARCEL_REJECTED or 503 PARCEL_SERVICE_UNAVAILABLE) can be retried with the same key.

External reference

externalRef is your own order number. It must be unique per merchant: a second order with the same reference is rejected with 409 DUPLICATE_EXTERNAL_REF, so it is also a safety net against double submission. You can look an order up by it.

Retrieving orders

Both calls need the orders:read scope and only return your own orders.

One order

GET /merchant-api/orders/{trackingNo} returns the order, or 404 NOT_FOUND.

List orders

GET /merchant-api/orders accepts externalRef, status, page (from 0) and size (up to 100, default 20). A live key lists live orders and a test key lists sandbox orders. The response is content plus page, size, totalElements and totalPages.

Order status lifecycle

An order moves forward through these statuses:

CREATED → ASSIGNED → PICKED_UP → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED or FAILED. After FAILED the parcel is RESCHEDULED or RETURNED. An order can be CANCELLED before it is delivered.

Rate limits

Each merchant account has a limit of requests per minute, shared by all its keys and clients (60 per minute unless SwiftDrop agreed another value with you; it is shown on your profile). The token endpoint is not counted. Over the limit you get 429 RATE_LIMITED: wait for Retry-After seconds, then retry.

Delivery and retries

  • Answer with any 2xx status within 5 seconds. That marks the delivery as successful. Do slow work after you have answered.
  • A timeout, a 5xx or a 429 is retried after @for (delay of retryDelays; track delay; let last = $last) { {{ delay }}{{ last ? '' : ', ' }} } (five retries), always with the same event ID.
  • Any other 4xx status fails the delivery immediately, with no retries. Do not answer with 4xx for events you simply do not care about.
  • Every attempt, with its result, is listed in the delivery log on the webhook page.

Verifying webhook signatures

Your endpoint is a public URL, so anyone can post to it. Treat an event as genuine only when all of these checks pass:

  1. Signature. Compute the hex HMAC-SHA256 of timestamp + "." + body with your signing secret, where timestamp is the X-SwiftDrop-Timestamp header and body is the raw request body, byte for byte. Compare it with X-SwiftDrop-Signature using a constant-time comparison. Parsing and re-serialising the JSON changes the bytes and breaks the signature.
  2. Freshness. Reject the event when the timestamp is more than 5 minutes away from your clock. This stops someone replaying a captured request.
  3. Duplicates. Delivery is at least once. Remember the X-SwiftDrop-Event-Id of processed events and answer 200 without doing the work again.
  4. Order. Events can arrive out of order. Keep the occurredAt of the last update per order and ignore older ones.

The examples keep processed event IDs in memory to stay short. Store them in a database or cache with an expiry (an hour is plenty) so duplicates are caught across restarts and servers.
